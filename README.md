# Local Qwen Optimization

## 專案目的

本專案旨在提出一套在不增加硬體成本的前提下，提升本地端大語言模型 (LLM) 推理效率與並發能力的技術方案。核心目標是將「Qwen 3.8-Flash-Next」這類 MoE (Mixture of Experts) 模型，從原本依賴單一顯存熱區與靜態路由策略的部署方式，提升成一套能在固定硬件上穩定運行的動態管理架構。

本方案建立在三層存儲與動態路由思想之上：
- 顯存：保存高熱度 expert
- 記憶體：保存中溫 expert
- SSD：保存冷 expert 以及查表資料

同時補足原方案中的關鍵弱點：
- 靜態熱區無法適應使用者分佈變化
- 顯存/記憶體交換過於頻繁
- CPU 排名與路由邏輯成為瓶頸
- SSD 讀寫壓力過大
- 多使用者並發時效率下降

---

## 1. 問題背景

原始的「Strata + Qwen 3.8-Flash-Next 4-bit」方案，其核心價值在於：
- 透過 4-bit 量化大幅降低模型佔用
- 透過路由機制把熱門 expert 留在較快層級
- 透過查表與預測減少大規模資料搬移

但這個方案仍有以下漏洞：

### 1.1 靜態 hot-expert 分配

原方案中，熱門 expert 是根據過去一段時間的流量統計做判斷；然而在真實場景中，使用者需求會浮動。某些長尾請求可能在短時間內突然暴增，造成之前被判定為「冷門」的 expert 變成熱點，導致：
- 顯存命中率急劇下降
- 記憶體交換頻率升高
- 推理延遲抖動

### 1.2 CPU 角色被低估

文章中的重點主要放在 GPU 和記憶體層次，但 MoE 的路由選擇、expert 排名、候選計算與預取策略，實際上仍大量依賴 CPU。當多個請求同時發生時，CPU 將變成新的瓶頸。

### 1.3 SSD 壓力過大

將大量冷 expert 與查表資料儲存在 SSD 上，雖然可節省顯存與記憶體需求，但頻繁存取會帶來：
- SSD 讀寫放大
- 寫入壽命下降
- 資料預取與 OOM 問題

### 1.4 多使用者並發問題

原方案幾乎是以單人單任務為場景描述，而本地部署中，常見情況是：
- 一個人持續連線
- 多人共用相同本地模型
- 不同請求帶來不同 token 分布

在這種情境下，固定熱區很容易失效。

---

## 2. 技術目標

在不增加硬體成本的前提下，本專案的技術目標如下：

1. 保持相同 GPU 與 RAM 配置下的可用性
2. 讓熱門 expert 能夠自適應重分配
3. 降低顯存 ↔ 記憶體 ↔ SSD 之間的交換頻率
4. 提升多請求並發下的吞吐與穩定性
5. 降低 SSD 寫損與 CPU 競爭
6. 讓整體系統在低成本架構上具有工程可維護性

---

## 3. 系統設計概覽

### 3.1 三層存儲架構

本方案延續三層模型，但將其擴展成「動態階層管理」：

- L1：顯存
  - 只保留真正熱的 expert 與關鍵路由表
  - 目標：最小化 GPU 記憶體交換

- L2：系統 RAM
  - 保存中等熱門 expert 與預取快取
  - 目標：降低 SSD 讀取壓力

- L3：NVMe SSD
  - 儲存冷 expert、查表、索引結構與長尾路由數據
  - 目標：擴大可用容量，保證可擴展性

### 3.2 動態熱區管理（核心改進）

原本方案將熱門 expert 固定在某一層，而本方案改為：
- 每固定時間窗口重新統計 expert 熱度
- 使用滑動窗口 + 加權指數平滑法更新熱度分布
- 對熱度變化進行分層重排

公式：

`hot_score = α × recent_usage + β × historical_usage + γ × concurrency_factor`

其中：
- `recent_usage`：近期請求命中率
- `historical_usage`：長期歷史命中率
- `concurrency_factor`：多併發下的壓力指標

這樣可以避免「熱區僵化」的問題。

## 4. 不增加硬體成本的漏洞補全方案

### 4.1 動態熱區重平衡

目標：在不增加 GPU/記憶體容量的情況下，讓 expert 分配更符合實時需求。

實作方式：
- 每 1–5 分鐘更新一次熱度分布
- 若某 expert 在近期命中率提升超過閾值，提升其優先級
- 若長時間未使用，將其逐步移往下層
- 在閾值之間使用平滑過渡避免抖動

效果：
- 減少需求變動造成的性能崩潰
- 讓熱區更貼近真實使用模式

### 4.2 預取與投機式路由

目標：提前識別下一個可能被使用的 expert，減少等待時間。

實作方式：
- 基於前一 token 的語義與路由分佈，預測下一個 expert
- 在 CPU 層預先排序候選 expert
- 若判斷高概率命中，則提前載入到 RAM 或顯存

這個流程可以降低：
- 專家切換造成的空轉
- 顯存 ↔ 記憶體搬運延遲

### 4.3 GPU/CPU 協同路由

目標：讓 routing 更具低延遲特性。

改進：
- 把 expert 排名計算一部分前移到 CPU
- GPU 負責真正的前向計算
- 避免 CPU 在高併發狀態下進入全局堵塞

優化策略：
- 讓 CPU 作為「候選預篩」層
- 用 GPU 執行最終 expert 參與決策
- 建立優先隊列來處理高優先級請求

### 4.4 SSD 寫入保護與內存介面優化

目標：降低 SSD 長期寫損與讀寫流量尖峰。

策略：
- 將 SSD 讀寫限流，避免讀寫大峰值
- 使用內存池做中間緩衝，將頻繁的小資料寫入合併
- 對冷 data 採用分批刷寫，而不是即時寫入
- 使用 page cache 分層設計，避免小文件造成大量散亂 I/O

### 4.5 多併發請求隔離

目標：讓模型在多人共用時不因熱區衝突而失效。

方案：
- 每個請求建立專屬路由上下文
- 對常用熱區做共享 cache，對長尾請求做隔離 cache
- 對不同請求分配不同優先級
- 若超出安全門檻，主動將低優先級請求移至較冷層

## 5. 具體實作方案

### 5.1 熱度監控模組

設計：
- 收集每個 expert 的命中次數、路由機率、查表命中率、最近一段時間 latency
- 每 1 秒更新一次 local stats
- 每 60 秒產生重分配決策

監控數據：
- expert hit rate
- miss rate
- swap rate
- latency percentile
- SSD I/O bandwith
- memory pressure

### 5.2 佈局控制器

責任：
- 在 L1/L2/L3 之間做 expert placement
- 根據熱度與帶寬情況動態調整
- 防止一個小范圍熱點導致全局性能退化

策略：
- 對熱門 expert 使用保護模式
- 對中等熱門 expert 使用預取模式
- 對冷 expert 使用滾動式保留策略

### 5.3 預取器（Prefetcher）

功能：
- 在下一輪推理前，預先分析 token 路徑
- 提前拉取可能邏輯路徑中的 expert
- 在請求開始前完成大部分 cache fill

這減少：
- 專家切換時的 latency
- 讀 SSD 或內存時的空轉

### 5.4 隔離式併發控制器

功能：
- 管理多個並發請求對 expert 的競爭
- 保證不讓單一重请求壓垮整體吞吐
- 使用令牌桶或優先隊列處理

## 6. 伺服器端應用策略

### 6.1 單機部署

適用場景：
- 單人本地部署
- 研究用途
- 小型團隊本地推理

優化重點：
- 保證 expert 熱區與 RAM 一致
- 使 SSD 存儲只保留冷尾部資料
- 允許該機持續處理 1–3 個高強度請求

### 6.2 多使用者共用部署

適用場景：
- 本地服裝／共享模型伺服器
- 小型團隊共用 LLM

優化重點：
- 引入優先級控制
- 使用共享 + 私有 cache 混合策略
- 根據不同使用者的熱度特徵分配分層資源

---

## 7. 性能目標

本方案預期達成：

1. 在相同硬體配置下，減少顯存與 RAM 交換帶來的抖動
2. 將熱區命中率提升到穩定區域
3. 降低顯著的延遲尖峰
4. 讓本地多請求負載保持可接受吞吐
5. 讓 SSD 自身負載保持在安全範圍內

### 7.1 指標

- expert hit rate（命中率）
- p95/p99 latency
- swap frequency
- CPU utilization
- SSD I/O utilization
- GPU utilization
- memory pressure

---

## 8. 測試策略

### 8.1 單請求測試

- 測驗單個長上下文 prompt
- 查看是否出現過高的資料交換
- 比較原始 stratified architecture 與新策略的延遲差異

### 8.2 多請求測試

- 模擬 2、4、8 個並發請求
- 驗證熱區穩定性與路由命中率
- 檢查 CPU 是否成為新瓶頸

### 8.3 長時間穩定性測試

- 持續 24–72 小時執行
- 觀察熱區漂移與 SSD 寫入壓力
- 確認系統在長時間運行中不會出現性能崩潰

---

## 9. 風險與應對

### 風險 1：熱區飄移過快

應對：
- 使用滑動窗口與平滑因子，避免瞬間波動造成過度重分配

### 風險 2：CPU 過載

應對：
- 把路由預篩拆成多層，降低單核壓力
- 適度把某些排序計算移到 GPU

### 風險 3：SSD 寫入過高

應對：
- 增加內存緩衝層
- 合併小寫入
- 透過批次異步寫入降低尖峰

### 風險 4：多請求互相干擾

應對：
- 使用優先級隊列
- 把共享熱區與私有工作區分開

## 10. 實施路線圖

### Phase 1：基線穩定
- 保留三層存儲結構
- 建立 expert heat map
- 基本路由統計與監控

### Phase 2：動態重排
- 加入熱度更新與窗口平滑
- 實現 L1/L2/L3 自動重分配

### Phase 3：預取與 CPU 協同
- 引入預取器
- 賦予 CPU 更明確角色

### Phase 4：多併發優化
- 加入優先級隊列
- 操作隔離和負載控制

### Phase 5：長期穩定最終化
- 觀測 SSD、RAM、CPU、GPU 全鏈路性能
- 形成統一的本地大模型部署標準

## 11. 結論

原始方案最關鍵的貢獻，是它將 MoE 模型從「單純依賴顯存」的思維，轉為「利用多層級存儲與路由管理」來增強實際可用性。這使它在本地端部署場景中具備很強的研究價值。

但如果只停留在靜態熱區與簡化路由，最終仍然會在：
- 併發負載
- 動態請求分布
- CPU 壓力
- SSD 寿命
- 長時間運行穩定性

這些面向出現瓶頸。

因此，本專案的核心貢獻，不是重新發明一個全新的模型架構，而是對現有三層架構做「動態管理 + 預取 + 併發隔離 + CPU/GPU 協作」的補強，使其在不增加硬體成本的情況下，形成更可靠、更適合本地端部署的日常運行方案。
